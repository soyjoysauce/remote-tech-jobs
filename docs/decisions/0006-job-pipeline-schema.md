# 0006: Job pipeline schema

- Status: Accepted
- Layer: 2
- Date: 2026-10-05

## Context

Layer 3 (ingestion) needs somewhere to write. The schema has to support re-ingesting the same listing many times a day, the same job appearing on more than one source, closing listings that disappear from their feed, and attribution for Remotive and Remote OK. It must fit in Supabase's 500 MB free tier, and every table in the `public` schema is reachable from the browser through the Data API.

## Decision

One migration, `create_job_pipeline_schema`, with four tables: `sources`, `companies`, `jobs`, `ingestion_runs`.

- **Upsert key.** `jobs` is unique on `(source_id, external_id)`. Ingestion upserts on that pair, so re-fetching a listing updates its row and bumps `last_seen_at`. `external_id` is text because sources use integers, uuids and slugs.
- **`dedupe_key` is indexed, not unique.** It is computed in app code from normalized company and title, to spot the same job on two sources. A unique constraint would make the second source's upsert fail, and would turn any flaw in the normalization into lost data. Both rows are kept and the listing query decides which to show.
- **Raw payloads are kept** in `jobs.raw` (jsonb), so a normalization bug can be fixed by re-processing stored data. Cost: roughly 10 to 20 KB per job before TOAST compression, about 50 to 100 MB per 5,000 jobs with the two description columns. Closed jobs are deleted after a grace period, and `raw` can be set to NULL on old rows.
- **Lifecycle.** `status` is `open` or `closed`, with a check that `closed_at` is set if and only if the status is `closed`. `posted_at` is the source's date; `first_seen_at` and `last_seen_at` are ours. `content_hash` says whether a listing changed; `updated_at` does not, because it moves on every run.
- **Types.** Enums for sets this project defines (`source_kind`, `job_status`, `ingestion_run_status`), which become unions in the generated TypeScript types. Text with a check constraint for values normalized from external data (`employment_type`, `salary_period`, `remote_region`), because those lists will change in Layer 3 and an enum value cannot be removed.
- **Keys.** `sources.id` is a readable text key (`greenhouse`). Other tables use `bigint` identity: half the size of a uuid in every index and foreign key.
- **Indexes.** A partial index on open jobs ordered by `posted_at desc nulls last, id desc` for the listing; `dedupe_key`; `company_id` (foreign keys are not indexed automatically); a partial index on `(source_id, last_seen_at)` for open jobs, for closing stale listings.
- **RLS on all four tables.** With RLS on and no policy, the publishable key sees nothing. The ingestion scripts use the secret key, which runs as `service_role`; that role has `BYPASSRLS`. Public read policies exist for open jobs, active companies and all sources. `ingestion_runs` has no policy.
- **Privileges as a second layer.** Supabase grants `anon` and `authenticated` every privilege on new `public` tables by default. The migration revokes them (tables and identity sequences) and grants back `select` on the three readable tables only. On `jobs` the grant is column by column and leaves out `raw`, `content_hash` and `dedupe_key`: RLS filters rows, not columns, and without this anyone with the publishable key could download every raw payload through the API.
- **Deferred.** No search vector (Layer 5), no embedding column (Layer 11), no user tables (Layer 7+). Each arrives in the migration of the layer that uses it.
- **Local ports.** The local stack uses ports 5532x instead of the default 5432x, because another local Supabase project on the owner's machine uses the defaults.

Schema behaviour is covered by pgTAP tests in `supabase/tests/database/`, and CI fails if the committed TypeScript types differ from what the migrations generate.

## Alternatives considered

- **Unique `dedupe_key`.** Rejected for the reasons above: it puts a heuristic in charge of data integrity.
- **Dropping the raw payload.** Saves space, but every normalization fix would need a full re-fetch, and Remotive asks for only a few API calls per day.
- **A separate `job_payloads` table for `raw`.** Keeps `jobs` rows narrow, but Postgres already moves large jsonb values out of line (TOAST), so listing queries that do not select `raw` do not read it.
- **uuid primary keys.** Useful when ids are generated by clients or must not be guessable. Neither applies here.
- **Enums everywhere, or check constraints everywhere.** All-enum makes Layer 3's changes to value lists awkward; all-check loses the TypeScript unions for the stable sets.
- **RLS only on tables with private data.** A table without RLS in `public` is writable by anyone holding the publishable key, so "it is public data anyway" still means anyone could delete it.
- **A view over `jobs` with only the public columns**, instead of a column-level grant. Views run with their owner's privileges unless created with `security_invoker`, so it is a second object whose RLS behaviour has to be got right. The column grant keeps one table and one set of policies.
- **Sources as a TypeScript constant instead of a table.** Simpler, but then `jobs.source_id` has no foreign key and attribution text cannot be joined in SQL.

## Consequences

- Layer 3 must upsert on `(source_id, external_id)`, set `content_hash` and `dedupe_key`, and write `ingestion_runs` rows.
- Queries that should use the partial indexes must include `status = 'open'`. The listing query must also order by `posted_at desc nulls last, id desc` exactly; without `nulls last` Postgres sorts instead of using the index. Layer 5 should decide whether to sort on a never-null key instead, since keyset pagination cannot compare NULL `posted_at` values.
- With the publishable key, `select *` on `jobs` fails. Queries list their columns, and a migration that adds a public column to `jobs` must also grant `select` on it.
- `seed.sql` only runs locally. The hosted project needs the five `sources` rows before the first ingestion run (`supabase db push --include-seed`, or a data migration in Layer 12).
- Adding a value to a check-constrained column needs a migration that replaces the constraint.
- `bigint` ids arrive in JavaScript as numbers. That is exact up to 2^53, far beyond what this table will reach.

## Interview talking points

- The upsert key is a real unique constraint and the dedupe key is only an index, because one is a fact from the source and the other is my heuristic.
- I keep the raw payload so I can fix normalization without re-fetching, and I worked out its storage cost against the free tier before deciding.
- RLS is on for every table, including ones with public data, because the publishable key ships in the browser and RLS is what stops writes. The secret key bypasses it through the `service_role` role's `BYPASSRLS` attribute.
- Partial indexes on open jobs keep the listing and stale-job indexes small, at the cost that queries must repeat the predicate.
- The `closed_at`/`status` rule is enforced by a check constraint in the database, so no code path can leave a job half-closed.
